# Paid API Guard

外部付费 API 调用的正确姿势是：**先零成本验证控制流 → 再小样本验证数据可用性 → 最后才放量**；每一步都要有硬预算和完整性断言。

把"昂贵的外部调用"当成「失败可重试的普通步骤」是一切问题的根源 —— 它其实是**不可回滚的支出**：花钱、不可控（限流/超时/欠费）、慢（分钟级反馈，错误发现得晚）。

## 何时用

- 写 / 跑任何调用付费外部 API 的代码或批量任务前（LLM、embedding、rerank、三方 SaaS）
- 设计评测、数据管道、批处理循环时
- 排查：额度白费、跑到一半中止、超时、限流、"运行成功但结果是空的"

## 三步走（顺序不能反）

1. **Dry-run 验控制流**：所有外部调用换成 mock，验证循环 / 重试 / 落库 / 失败处理 / 进度 / 断言全对。**零成本**，绝大多数坑在这一步暴露。
2. **小样本验数据可用**：1~3 条跑通**完整链路**（含判分、落库），确认"拿到的数能用"。
3. **放量**：带硬预算和完整性断言才放量。

## 铁律（从血泪里来的）

1. **失败必须"响"，不能静默**：宁可误报失败，不可漏报成功。"运行成功但数据是空的"是最贵的坑。
2. **错误分类用白名单**：只对明确可重试的错误（超时/连接失败）重试，其余一律中止。黑名单漏一个就空跑。
3. **一次只改一个变量**：否则拿到的数据没法归因，等于白跑。
4. **阶段产出落库**：让后续阶段可独立重放，别动不动重跑整条昂贵链路。
