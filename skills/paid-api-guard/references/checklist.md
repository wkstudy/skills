# 动手前检查清单

调用任何付费外部 API（含批量/循环）之前，逐项过。每项都给了"怎么查"，别拍脑袋。

## 1. 并发

分三层看，**关键是它们会相乘**——只看单层会严重低估实际并发。

- [ ] **代码层**：单进程内的并发上限（协程/线程数、连接池 `pool_size` / `max_overflow`、MQ prefetch/qos）。查配置或代码。
- [ ] **容器/编排层**：**副本数 × 每副本 worker 进程数**。连接池是**每进程**的 → 总连接数 = 副本数 × 进程数 × pool_size，容易打爆自己的 DB / 下游。
- [ ] **调用方 SDK 层**：SDK 的**默认并发**（最容易忽略，是你没设的隐藏值）。读 SDK 源码找默认值。
- [ ] **算一遍有效总并发** = 副本 × 每副本进程 × 每进程 SDK 并发。用它对照下游速率上限，而不是用单层的数字。
- [ ] **下游能否承受**：有效总并发 vs 下游 / 连接池 / TPM-RPM 上限。
- [ ] ⚠️ **并发不是越高越好**：并发高 → 单次请求变慢 → 撞上"单次超时"；并发高 → 连接池耗尽 → 请求被拒/消息被丢。先测单次耗时再定并发。

## 2. 耗时

- [ ] 单次调用的 **P50 / P95**（大 prompt / 大 payload 会显著变慢）。先跑 3 条实测，别估算。
- [ ] **总耗时估算** = 调用总数 / 并发 × 单次耗时。先算一遍，再决定跑不跑。

## 3. 超时

- [ ] 调用方超时的**默认值是多少**？**能不能调**？读源码找硬编码值。
- [ ] 调不了时的对策：**降并发 + 缩输入 + 拆批次**。
- [ ] 超时与重试的关系：超时后重试 = **再花一次钱**。

## 4. 配额（TPM / RPM）

- [ ] TPM（tokens/分钟）/ RPM（requests/分钟）上限是多少？
- [ ] 单次调用消耗多少 token → 每分钟能跑多少次。
- [ ] **换算校验**：并发数 × 单次 token / 单次耗时 是否超 TPM。
- [ ] ⚠️ **查不到上限时**（文档不写 / 随账号档位变 / 不公开），按顺序兜底：
  1. 先查文档、响应头、厂商控制台后台；
  2. **查不到就问用户** —— 用户往往知道自己的账号档位，或能去控制台查到；
  3. 仍不确定 → **低并发（1~2）起步 + 把 429 当探测信号做指数退避**，让限流器自己找到天花板；同时从响应用量反推实际速率。
  4. 前提：**429 必须在可重试白名单里**，否则一撞就崩（见 patterns.md）。

## 5. 计费

- [ ] 免费额度 / 付费额度 / **欠费**是不同状态，错误码/文案**各不相同**（穷举它们）。
- [ ] 有没有**硬预算熔断**（累计调用数 / 估算花费到阈值就停），而不是靠"额度用完报错"来兜底。
- [ ] 失败的调用会不会也扣费 / 扣配额。

## 6. 失败语义

- [ ] 哪些错误**可重试**（超时、连接失败），哪些**必须停**（欠费、参数错、内容违规）—— 用**白名单**（只重试可重试的）。
- [ ] **部分失败**怎么处理：绝不能"部分成功就整体标成功"。
- [ ] **完整性断言**：收尾前检查"应有 N 条、实际 M 条"，不全就失败。
- [ ] 重试有**上限**且**可见**（次数计入日志），别默认重试 10 次白烧 10 倍。
- [ ] 昂贵阶段的产出**落库**，让后续阶段可独立重放，不用重跑整条链路。
