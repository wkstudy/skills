# 动手前检查清单

调用任何付费外部 API（含批量/循环）之前，逐项过。每项都给了"怎么查"，别拍脑袋。

## 1. 并发

- [ ] **自己进程的并发上限**：连接池大小（`pool_size` / `max_overflow`）、协程/线程数。查配置或代码。
- [ ] **调用方 SDK 的默认并发**（最容易忽略——它是你没设的隐藏值）。读 SDK 源码找默认值。
- [ ] **下游能否承受**：并发数 vs 下游速率上限。
- [ ] ⚠️ **并发不是越高越好**：并发高 → 单次请求变慢 → 撞上"单次超时"。先测单次耗时再定并发。

## 2. 耗时

- [ ] 单次调用的 **P50 / P95**（大 prompt / 大 payload 会显著变慢）。先跑 3 条实测，别估算。
- [ ] **总耗时估算** = 调用总数 / 并发 × 单次耗时。先算一遍，再决定跑不跑。

## 3. 超时

- [ ] 调用方超时的**默认值是多少**？**能不能调**？读源码找硬编码值。
- [ ] 调不了时的对策：**降并发 + 缩输入 + 拆批次**。
- [ ] 超时与重试的关系：超时后重试 = **再花一次钱**。

## 4. 配额（TPM / RPM）

- [ ] TPM（tokens/分钟）/ RPM（requests/分钟）上限是多少？
- [ ] 单次调用消耗多少 token → 每分钟能跑多少次。
- [ ] **换算校验**：并发数 × 单次 token / 单次耗时 是否超 TPM。

## 5. 计费

- [ ] 免费额度 / 付费额度 / **欠费**是不同状态，错误码/文案**各不相同**（穷举它们）。
- [ ] 有没有**硬预算熔断**（累计调用数 / 估算花费到阈值就停），而不是靠"额度用完报错"来兜底。
- [ ] 失败的调用会不会也扣费 / 扣配额。

## 6. 失败语义

- [ ] 哪些错误**可重试**（超时、连接失败），哪些**必须停**（欠费、参数错、内容违规）—— 用**白名单**（只重试可重试的）。
- [ ] **部分失败**怎么处理：绝不能"部分成功就整体标成功"。
- [ ] **完整性断言**：收尾前检查"应有 N 条、实际 M 条"，不全就失败。
- [ ] 重试有**上限**且**可见**（次数计入日志），别默认重试 10 次白烧 10 倍。
- [ ] 昂贵阶段的产出**落库**，让后续阶段可独立重放，不用重跑整条链路。
