# 案例库

每踩一个坑加一条。**格式固定，`检测方法` 必填** —— 没有"下次怎么提前发现"的案例只是故事，不是防御。

每条都以「场景」开头，保证脱离具体项目也能读懂。

案例格式：

```
### [YYYY-MM-DD] 一句话现象
- 场景：陌生读者也能看懂的背景（一句话）
- 现象：观察到的错误表现
- 根因：为什么发生
- 代价：白花了多少（钱 / 时间 / 几轮）
- 对策：怎么改
- 检测方法：下次怎么在花钱之前发现   ← 必填
- 适用平台：
```

### [2026-09-23] 计费错误分黑名单漏检，欠费没识别到，整批空跑
- 场景：批量调用某云厂商的 LLM API 跑任务。
- 现象：代码里判断"是不是额度/计费问题"时只匹配了 `quota` 这个词；账号**欠费**时厂商返回的错误里不含 `quota`，没被识别 → 程序继续往下跑，后面每一条都失败，白跑到底。
- 根因：错误分类用了**黑名单**（列举"要中止"的错误特征），只要漏一种就漏防。同一家厂商，"免费额度用完"和"账号欠费"是两种不同错误、文案完全不同。
- 代价：约 25/37 条调用空跑。
- 对策：改用**白名单** —— 只对明确可重试的错误（超时、连接失败）重试并继续，其余一律中止。新出现的错误类型默认被当成"要停"，天然安全。
- 检测方法：dry-run（见 patterns.md）注入各种错误码，确认"非白名单错误一律中止"；代码里搜有没有 `if "关键词" in err: 停` 这种黑名单写法。
- 适用平台：通用（云厂商 LLM API 尤甚）

### [2026-09-23] 整段失败却被标成"成功"
- 场景：一个"跑任务 → 用程序打分 → 落库"的批处理。
- 现象：打分阶段整段失败（分数全为空），但收尾逻辑只更新了状态字段，把运行标成了 `success`，看起来像有效结果。
- 根因：收尾只置状态，没校验"到底有没有产出"。
- 代价：一整轮结果作废，而且当时没察觉 —— 比直接报失败更危险，因为它伪装成成功。
- 对策：收尾前做**完整性断言**，产出为空一律标失败。
- 检测方法：dry-run 让所有调用返回空，确认运行被标 failed 而不是 success。
- 适用平台：通用

### [2026-09-23] 部分失败也被当成功
- 场景：同上批处理，应处理 36 条，只成功 14 条，其余超时失败。
- 现象：仍被标成功。
- 根因：完整性断言只判了"全空"，没判"缺了一部分"。
- 对策：断言口径改成"应有 N 条、实得 M 条，M < N 即失败"，并列出缺失项。
- 检测方法：dry-run 让一半样本失败，确认运行判 failed 并报出缺失清单。
- 适用平台：通用

### [2026-09-23] 调用方 SDK 超时写死 60 秒且不给调
- 场景：用某评测库（arize-phoenix 的 evals 模块）批量调 LLM 打分。
- 现象：输入 prompt 一大，单次调用就超过 60 秒，大面积超时失败。
- 根因：库内部的执行器把单次超时**硬编码为 60 秒**，且对外函数参数里不暴露这个值，没法调大。事先没读源码，以为超时可配。
- 代价：约 22/36 条超时白跑。
- 对策：超时调不了时，**从两头绕**——降并发（让单次更快返回）+ 缩输入（prompt 压小）。
- 检测方法：接任何新 SDK 前，先读源码确认"单次超时默认值 + 能否配置"；先跑 1 条量出单次耗时，和超时阈值比。
- 适用平台：arize-phoenix evals（executor 默认 timeout=60，见 platforms.md），但"SDK 藏死超时"是通用坑

### [2026-09-23] 并发太高→互相争用→单次变慢→撞超时
- 场景：批量调 LLM，想用高并发跑快点。
- 现象：默认高并发时大量超时；把并发降到 3 反而全部正常。
- 根因：并发太高时每次调用互相争用资源，单次耗时被拉长，超过了超时阈值 → 越并发越慢越超时。
- 对策：并发不是越高越好；当"单次耗时"接近"超时阈值"时，降并发反而更快更稳。
- 检测方法：先测单次耗时与超时阈值的比值，比值高就压并发。
- 适用平台：通用（单次较慢的大模型调用尤甚）

### [2026-09-23] 默认重试 10 次，超时/欠费场景白烧 10 倍
- 场景：用带自动重试的 SDK 批量调用。
- 现象：欠费或超时时，同一条被重试到第 10 次才放弃，每条白花约 10 倍。
- 根因：没设重试上限，用了 SDK 的默认次数；且不可重试的错误也进了重试循环。
- 对策：显式设重试上限；不可重试的错误（白名单之外）第一次就停。
- 检测方法：看日志有没有同一条重试很多次；确认不可重试错误不进重试循环。
- 适用平台：通用

### [2026-09-23] 一轮同时改两个变量，结果无法归因
- 场景：迭代一个"用 LLM 给答案打分"的评分器。
- 现象：一轮里同时换了"用哪个模型打分"和"喂给打分器的输入内容"，跑完分数变了，但分不清是哪个改动造成的。
- 根因：一次改了多个变量。
- 代价：那一轮（花了钱的）数据等于白跑。
- 对策：一次只改一个变量。
- 检测方法：动手前列出"这次改了什么"，超过 1 项就拆成多轮。
- 适用平台：通用（评测 / 对比类任务尤甚）

### [2026-09-23] 喂给打分器的证据只有 10%，正确答案被误判成编造
- 场景：一个 Agent 先调工具查资料再作答，然后用另一个 LLM（当"裁判"）核对"回答有没有依据"。
- 现象：裁判把明明有依据的回答判成"编造"。实际是：Agent 用了十几次工具（检索 + 直接读文件），但喂给裁判的只有其中检索那 1~2 次的结果，直接读文件得到的内容全漏了 → 裁判看到的证据不足 10%。
- 根因：只捕获了一部分工具调用的产出，漏了其余来源。
- 代价：跑了 36 分钟全量才发现结论不可信，还一度把锅扣给"裁判太严"。
- 对策：喂给裁判的材料要覆盖 Agent 实际用过的**全部**证据来源。
- 检测方法：判分前断言"证据覆盖率"——Agent 调了 N 次取数工具，喂给裁判的上下文里就该有这 N 次的产出（或明确的截断说明）；小样本先人工核对一条"裁判看到的 == Agent 用到的"。
- 适用平台：通用（Agent + LLM 裁判 架构）

### [2026-09-23] 队列消费无并发上限→连接池耗尽→消息被丢弃
- 场景：用消息队列（RabbitMQ / aio-pika）做异步处理，消费者从队列取任务、每个任务要占一个数据库连接。
- 现象：大量任务卡在中间状态；重新触发同步又跳过它们，数据一直补不齐。
- 根因：消费者没设 prefetch（一次预取上限），无上界拉取 → 峰值约 156 条并发处理 → 每条占一个 DB 连接，而连接池上限只有 15（`pool_size=5 + max_overflow=10`）→ 池耗尽 → 任务异常 → 消息被 **reject 丢弃**（不是重回队列）→ 下次同步因内容哈希没变而跳过 → 数据永久缺失。
- 代价：58 条卡死，排查加恢复耗时。
- 对策：① 给每层并发设上界（`set_qos(prefetch_count=1)`）；② 中间态记录在重同步时重跑，不靠哈希判断。
- 检测方法：动手前算"有效总并发"（这里 = 消费者无上界 → 远超连接池 15），对照连接池/下游上限；任何"从队列或流里无上界取"的地方都要显式设 prefetch / 批大小。
- 适用平台：RabbitMQ / aio-pika（默认无 prefetch 上限），通用于任何 MQ 消费者

### [2026-09-23] 不知道对方 TPM/RPM 上限就盲跑
- 场景：调第三方 API，但对方没公开限流阈值（TPM=每分钟 token 数 / RPM=每分钟请求数），文档不写、随账号档位变。
- 现象：无法预先算"安全并发"，只能盲跑；要么撞 429 限流大量重试变慢，要么侥幸没撞但离天花板多近全靠运气。
- 根因：把"配额未知"当成"配额无限"来跑。
- 对策（按顺序）：① 查——文档 / 响应头 / 厂商控制台后台；② **查不到就问用户**（用户往往知道自己的账号档位，或能去控制台查）；③ 仍不确定——低并发（1~2）起步 + 把 429 当探测信号做指数退避，让限流器自己找到天花板；同时从响应用量反推实际速率。
- 检测方法：动手前确认"TPM/RPM 是否已知"；未知时默认走"低起步 + 429 退避"，且 429 必须在可重试白名单里（否则一撞就崩）。
- 适用平台：通用
