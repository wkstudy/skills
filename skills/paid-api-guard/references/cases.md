### [2026-09-23] 免费额度耗尽与欠费是两种错误，黑名单漏检导致空跑
- 现象：额度检测只认 `quota` 字样，认不出 `Arrearage`（欠费，400），运行一路空跑到底。
- 根因：错误分类用了黑名单（列举要中止的错误），漏一个就漏防。免费额度耗尽是 `403 Free quota exhausted`，欠费是 `400 Arrearage / Access denied ... in good standing`，文案完全不同。
- 代价：空跑 25/37 题。
- 对策：改用**白名单**——只对明确可重试的错误（超时/连接）重试，其余一律中止。
- 检测方法：dry-run 时注入各种错误码，确认"非白名单错误一律中止"；代码里搜有没有 `if xxx in err: stop` 这种黑名单写法。
- 适用平台：百炼 dashscope（错误码见 platforms.md）

### [2026-09-23] 判分全失败但运行被标成 success
- 现象：judge 阶段因欠费全部失败、分数全空，但运行状态写成 `success`，页面显示成有效基线。
- 根因：收尾只置状态，没校验产出完整性。
- 代价：一整轮结果作废，且当时没察觉（比直接失败更危险）。
- 对策：收尾前做完整性断言，0 条或部分缺失都置 failed。
- 检测方法：dry-run 让所有判分返回空，确认运行被标 failed 而非 success。
- 适用平台：通用

### [2026-09-23] 部分失败也被当成功
- 现象：36 条判分只成功 14 条，仍标 success。
- 根因：完整性断言只判"全空"，没判"部分缺"。
- 对策：断言覆盖"应有 N 条、实得 M 条，M<N 即失败"。
- 检测方法：dry-run 让一半样本失败，确认运行判 failed 并列出缺失题号。
- 适用平台：通用

### [2026-09-23] 调用方超时硬编码 60s 且不透出参数
- 现象：Phoenix `async_evaluate_dataframe` 的 executor 超时写死 60s，大 prompt 必然超时，且函数签名不暴露 timeout。
- 根因：没读 SDK 源码，以为超时可配。
- 代价：22/36 条 worker timeout 白判。
- 对策：调不了 timeout 时，**降并发 + 缩输入**绕开（并发 3、上下文压到 4K）。
- 检测方法：接一个新 SDK 前，先读源码确认超时默认值和能否配置；先跑 1 条量单次耗时对比超时值。
- 适用平台：arize-phoenix evals（executor 默认 timeout=60，见 platforms.md）

### [2026-09-23] 默认并发过高 → 争用 → 单次变慢 → 撞超时
- 现象：判分默认高并发时大量超时；降到 concurrency=3 后正常。
- 根因：并发高使每次调用互相争用，单次耗时被拉长到超过超时阈值。
- 对策：并发不是越高越好；单次耗时接近超时阈值时，降并发反而更快更稳。
- 检测方法：先测"单次耗时"与"超时阈值"的比值，比值高就压并发。
- 适用平台：通用（尤其单次慢的大模型判分）

### [2026-09-23] 默认重试 10 次，超时场景白烧 10 倍
- 现象：欠费/超时时 executor 重试到第 10 次才放弃，每条白花 10 倍。
- 根因：没设重试上限，用了 SDK 默认值。
- 对策：显式设重试上限；不可重试的错误（白名单外）第一次就停。
- 检测方法：看日志有没有同一条重试很多次；确认不可重试错误不进重试循环。
- 适用平台：通用

### [2026-09-23] 同时改两个变量，数据无法归因
- 现象：一轮里同时换了 evaluator（Faithfulness→自定义）和判分输入，跑完分不清分数变化来自哪个。
- 根因：一次改了多个变量。
- 代价：那轮数据等于白跑。
- 对策：一次只改一个变量。
- 检测方法：动手前列出"这次改了什么"，超过 1 项就拆成多轮。
- 适用平台：通用（评测/对比类任务尤甚）
