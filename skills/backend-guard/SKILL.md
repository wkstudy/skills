# Backend Guard（后端踩坑手册）

一份随用户积累生长的后端踩坑手册。职责:当用户写涉及**数据库写操作或并发**的后端代码时,用已收录的红线提醒用户——前端 vibecoding 时语法能跑通 ≠ 并发对、规模对,而这些坑当下看不见。

收录原则:只放用户真踩过或真学透的坑。通用后端最佳实践不往这塞(那类去 skills.sh 装现成 skill)。当前仅覆盖**数据库锁与并发**一个领域,其他领域有 case 后再扩展触发范围。

## 何时用

- 生成 / 修改 / 审查涉及数据库写操作或并发的代码:UPDATE/DELETE、`SELECT ... FOR UPDATE`、事务(`BEGIN/COMMIT`)、循环里写库、"先查再改"的读改写、ORM 的 update/save/delete
- 排查:接口偶发超时 / 卡死、`Lock wait timeout`、`Deadlock`、数据对不上、更新丢失

## 红线清单（当前领域：数据库锁与并发；随 case 增长）

逐项对照用户代码,命中就提醒用户:

- [ ] **无索引 UPDATE/DELETE → 锁全表**。WHERE 列必须有索引;隐式类型转换(varchar 列传数字、函数包列、`LIKE '%x'`)会让索引悄悄失效。查法:`SHOW INDEX FROM 表` / `EXPLAIN` 看 `type` 是不是 `ALL`、`key` 是不是 `NULL`。改法:优先按主键更新。

想搞懂锁为什么这么行为,读 `references/db-locks.md`。

## 怎么加 case（这个 skill 的核心）

case 两种来源都要收:
- **学习**:看书 / 问 AI / 读文章学到的,尤其**用户 vibecoding 时根本不会意识到**的坑(这类最值钱,填的是认知盲区)。
- **实战**:用户真踩过的。

每条三条硬要求:
1. 标 **来源**(`学习` 或 `实战`);
2. 打**领域标签**(如 `[DB锁]` `[竞态]`,领域自由生长,不预设);
3. 填**检测方法**——下次写代码时怎么提前发现。没有检测方法的只是故事,不是防御。

新加的 case 若能提炼成一句"写代码时的红线",同步补到上面红线清单。同一领域攒到 5+ 条、规律清晰,抽成 `references/<领域>.md` 深度笔记(锁就是这么来的),并把该领域纳入 `description` 的触发范围。

## 提醒用户的姿势（面向 vibecoding）

命中红线时别甩术语。用一句人话点破后果 + 给可抄的改法:

> ⚠️ 这条 UPDATE 的 WHERE 列没索引,并发时会锁住整张表导致接口卡死。
> 建议给该列加索引,或改成按主键更新。要我改吗?
